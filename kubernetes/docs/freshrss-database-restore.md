# Restore the FreshRSS database

Backup source: CronJob `freshrss-database-dump` (namespace `development`,
`kubernetes/development/freshrss.yaml`). Daily `pg_dump --format=custom` to
`/data/backups/freshrss/freshrss-<YYYY-MM-DD>.dump` on home-server, kept 7
days. `/data/backups` is also in the restic backup (Hetzner storage box).

Scope: database only (feeds, articles, users). The `freshrss-data` PVC
(config, extensions) is not covered.

## 1. Get the dump

Local copy still present:

```sh
ls -l /data/backups/freshrss/
```

Disk lost or dump older than 7 days, pull it from restic (wrapper generated by
`services.restic.backups.remotebackup`):

```sh
sudo restic-remotebackup snapshots
sudo restic-remotebackup restore latest --target /tmp/restore --include /data/backups/freshrss
ls /tmp/restore/data/backups/freshrss/
```

Check the dump is readable:

```sh
pg_restore --list /data/backups/freshrss/freshrss-YYYY-MM-DD.dump | head
```

## 2. Stop the app

```sh
kubectl -n development scale deploy/freshrss --replicas=0
```

## 3. Make sure the cluster exists

```sh
kubectl -n development get cluster freshrss-database
kubectl -n development get pod freshrss-database-1
```

Cluster gone: `kubectl apply -f kubernetes/development/freshrss.yaml`, wait for
`Cluster in healthy state`. `initdb` recreates an empty `freshrss` database
owned by `freshrss`.

## 4. Restore

Stream the dump into the primary. Runs as `postgres` over the local socket,
`--role` makes restored objects owned by `freshrss`.

```sh
DUMP=/data/backups/freshrss/freshrss-YYYY-MM-DD.dump
kubectl -n development exec -i freshrss-database-1 -c postgres -- \
  pg_restore --clean --if-exists --no-owner --role=freshrss --dbname=freshrss \
  < "$DUMP"
```

`--clean --if-exists` drops existing objects first, so this overwrites current
data. Harmless warnings about objects not existing on an empty database are
expected. Any other error: stop and read it before continuing.

## 5. Start the app and verify

```sh
kubectl -n development scale deploy/freshrss --replicas=1
kubectl -n development rollout status deploy/freshrss
kubectl -n development exec freshrss-database-1 -c postgres -- psql -d freshrss -c '\dt'
```

Open `http://home-server:30005`, check feeds and recent articles are present.

## Troubleshooting: `password authentication failed for user "freshrss"`

Typical after the Cluster was recreated: CNPG generated a new
`freshrss-database-app` password, but FreshRSS only reads `FRESHRSS_INSTALL` on
first start and afterwards uses the password saved in `data/config.php` on the
`freshrss-data` PVC, which is the old one.

1. Compare the secret with `config.php`:

   ```sh
   kubectl get secret freshrss-database-app -o jsonpath='{.data.password}' | base64 -d; echo
   kubectl exec deploy/freshrss -- grep -n "'password'" /var/www/FreshRSS/data/config.php
   ```

2. If they differ, update `config.php` and restart:

   ```sh
   kubectl exec -it deploy/freshrss -- sed -i "s/'password' => '[^']*'/'password' => 'NEW_PASSWORD'/" /var/www/FreshRSS/data/config.php
   kubectl rollout restart deploy/freshrss
   ```

   If they match, check the role exists in Postgres:

   ```sh
   kubectl -n development exec freshrss-database-1 -c postgres -- psql -c '\du freshrss'
   ```

## Notes

- Sibling dumps from older days are untouched by a restore.
- Test the procedure on a scratch database before relying on it:
  `createdb -O freshrss freshrss_test` then restore with `--dbname=freshrss_test`.
